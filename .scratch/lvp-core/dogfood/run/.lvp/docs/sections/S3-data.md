# S3 — Data & privacy

## Answers
- **S3.q1 Apakah orang harus punya akun dulu di aplikasi ini sebelum bisa memakainya, atau siapa pun yang punya tautan bisa langsung mulai?** — Admin — saya — perlu login dong, soalnya yang pegang uang dan jadwal. Tapi pemain nggak usah bikin akun, ribet. Cukup isi nama dan nomor HP pas booking. · _EN: Auth fork answered: the admin (owner) logs in; players need no account — they book with just a name and phone number. Two-tier auth model, one credential set total (D-010)._
- **S3.q2 Data apa saja tentang seseorang yang akan disimpan aplikasi ini — nama, nomor HP, foto, lokasi, atau hal lain tentang mereka?** — Namanya, nomor HP-nya, jadwal bookingnya, dan status DP-nya — sudah, nggak perlu lain-lain. Nggak ada foto KTP atau apalah. · _EN: PII inventory (human-facing): name, phone number, booking schedule, DP/payment status. Nothing else volunteered — which triggered the technical-traces surface (D-013)._
- **S3.q3 Apakah ada uang yang berpindah di dalam aplikasi ini — jual-beli, langganan, tip, atau tidak ada sama sekali?** — Ada — DP 30% tiap booking. Pengennya sih DP-nya online langsung, biar pemain tinggal bayar dan saya tinggal lihat. Nggak ada jualan lain. · _EN: Money moves in the app: the 30% DP per booking; nothing else is sold. The user's desire is a fully online DP — the DESIRE is recorded here; the chosen v1 METHOD in S3.q5 is manual (see D-011 flag)._
- **S3.q4 Untuk login admin: mau masuk pakai akun yang sudah ada — misalnya akun Google — atau username dan password baru khusus aplikasi ini?** — Username dan password biasa saja, khusus aplikasi ini. Akun Google juga ada sih, tapi biar sederhana. (Catatan desain soal jejak teknis tadi: oke, setuju.) · _EN: Admin signs in with a dedicated username + password (no Google/OAuth dependency). The user also explicitly accepted the technical-traces decision surfaced just before this batch (D-013)._
- **S3.q5 Tadi Anda bilang pengennya DP online. Untuk mulai, mau bagaimana mekanismenya — langsung gateway pembayaran otomatis, atau cara lain dulu?** — Transfer manual dulu, admin konfirmasi — nanti kalau ramai baru gateway otomatis. Jadi aplikasinya nggak pegang data kartu sama sekali. · _EN: v1 payment method: manual bank transfer, admin confirms after checking m-banking; automatic gateway only "when it gets busy". No card data stored anywhere — the app never touches card numbers (SECURITY.md scope). CONFLICT SEED for S5/S6 (D-011): the day-one task (S1.q9) says "bayar DP 30% online" but the chosen v1 method is manual — the feasibility loop must confront desire vs method with cost/workload data._
- **S3.q6 Selain urusan uang, aplikasi ini akan terhubung ke layanan lain nggak — peta, WhatsApp, pengiriman email, atau layanan AI?** — Kayaknya nggak ada. Oh, kalau email atur-ulang password tadi itu ya layanan pengirim emailnya. Selain itu nggak — WhatsApp tetap di luar aplikasi, seperti sekarang. · _EN: Third-party list: one — an email-sending service for password resets (D-012). WhatsApp stays outside the app exactly as today (S1.q5 workaround is partially kept)._
- **S3.q7 Dari data tadi — nama, nomor HP, jadwal, status DP — adakah yang bakal terasa seperti pengkhianatan kalau dilihat orang asing? Hal kesehatan, uang, anak-anak, nomor identitas?** — Nama dan nomor HP sih biasa. Tapi status DP sama nominal bayarannya urusan uang — kalau bocor atau salah catat, ribut sama pemain. Itu yang paling harus dijaga. · _EN: Sensitivity bar sits on the money fields: DP status and amounts are the must-protect fields; name/phone are ordinary. Drives per-field protection in SECURITY.md._
- **S3.q8 Kalau internet tiba-tiba mati, apakah aplikasi ini harus tetap bisa dipakai — sama sekali harus, sedikit saja, atau tidak perlu?** — Nggak usah. Kalau internet mati ya pemain memang nggak bisa booking — wajar. Yang penting pas normal jalan terus dan nggak dobol. · _EN: No offline requirement at all — online-only web app is acceptable; the real concern is correctness when online ("nggak dobol", no double-bookings — echoes D-004). No offline-first storage decisions needed._
- **S3.q9 Siapa boleh melihat data siapa — cuma pemiliknya sendiri, sekelompok, atau semua orang?** — Pemain cuma boleh lihat jadwal lapangan dan bookingnya sendiri. Saya sebagai admin lihat semua — ya toh saya pemiliknya. · _EN: Access model: players see the court schedule and only their own bookings; the admin sees everything. Consistent with the two-role views from S1 (D-003) — no admin "see everything" surface was needed; it is the user's own words here._
- **S3.q10 Kalau ada orang minta Anda hapus semua data tentang dirinya, apa yang sebaiknya terjadi?** — Ya dihapus saja semuanya — namanya, nomornya, bookingannya. Kan datanya kecil, nggak ada yang perlu disimpan diam-diam. · _EN: Erasure = delete everything about the person, nothing retained (data is small). The existence of a working delete path is recorded as D-015 (designer_filled — erasure is a duty, not a feature request); the user's answer supplies its behavior._

## Decisions this Section
- **D-010** Admin-only login (username + password); players book without any account, identified by name + phone number — User's own choice (S3.q1, S3.q4): only the owner logs in; the player flow stays accountless for simplicity · status: user_confirmed
- **D-011** v1 payments: manual bank transfer + admin confirmation; automatic payment gateway deferred until volume grows; no card data ever stored — User wants an online DP eventually (S3.q3, S1.q9) but chose manual-transfer-first (S3.q5). FLAG for S5/S6: v1 method is manual while the recorded day-one expectation says online — the feasibility loop must confront this with gateway fees (vs the Rp 100.000 ceiling, D-005) and the admin-confirmation workload at 20-30 bookings/week (S1.q6) · status: user_confirmed
- **D-012** Password-reset by email for the admin account — requires an email-sending service — designer_filled: nobody asks what happens after "forgot password"; surfaced with the login confirmation, user accepted · status: designer_filled
- **D-013** Technical traces (IP addresses, error logs, device signals) count as personal data and join the PII inventory — designer_filled: the user listed human-facing facts only (S3.q2); surfaced proactively, user accepted · status: designer_filled
- **D-014** A plain-language privacy policy page exists at launch — designer_filled per the S3 decision surface (any login + any personal data makes it mandatory; never a question); shown visibly, user accepted ("Oke, setuju semua") · status: designer_filled
- **D-015** A working "delete my data" path exists at launch: a player (or the admin) can erase a person — name, phone, bookings — completely — designer_filled: erasure is a duty, not a feature request; the user's S3.q10 answer supplies the behavior (delete everything, nothing retained) · status: designer_filled
